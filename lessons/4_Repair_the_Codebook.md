# Step 6 — Compare your Version 2 with someone else

Read your new definition to a partner.

Then ask:

- Where are our definitions still different?
- Did one of us require explicit emotional language?
- Did one of us include material conditions more broadly?
- Did one of us write a definition that is too broad to be useful?
- Did one of us write a definition so narrowly that obvious cases disappear?

You do not have to end with identical wording.

The goal is to see whether the remaining differences are now **visible and discussable**.

---

# What did we actually repair?

We did not repair the AI.

We repaired the **research instrument**.

That distinction matters.

When an AI system gives inconsistent or questionable coding, there are several possible responses:

- change the model;
- change the prompt;
- check the source more carefully;
- or improve the codebook.

In qualitative research, the last option is easy to overlook.

But repeated disagreement can reveal that the code itself is doing too much work.

---

# A stronger codebook changes the AI task

Compare these two instructions:

> “Code this passage for hardship.”

and:

> “Apply `T2-HARDSHIP` only when the passage describes a materially, physically, socially, or emotionally adverse condition **and** the text gives evidence that the condition is experienced, framed, or treated as consequential. Do not infer hardship solely from historical knowledge that the situation was exploitative.”

The second instruction is not automatically the correct definition for your project.

But it is more **auditable**.

A reader can argue with it.

A model can be checked against it.

And you can revise it again.

That is the point.

## Takeaway

AI-assisted qualitative coding is not only about scaling up the application of a finished codebook.

It can also expose where the codebook itself is unstable.

The useful workflow is:

> **code → compare → audit → revise → test again**

The human judgment does not disappear.

It moves to a different part of the process.
